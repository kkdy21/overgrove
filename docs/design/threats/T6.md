# T6. 저장소 로컬 `credential.helper` 실행

> 상태: Accepted (Phase 2 게이트, 2026-11-05, #457에서 [security-review.md](../security-review.md) §2를 위협별로 나눔) · 관련: [security-review.md](../security-review.md) (범위·가정 §1, 최종 규칙 §3, 실험 기록 §4, 체크리스트 §5, S-05 근거 §6)

- **설명**: 원격 인증이 필요할 때 git은 system → global → local 순서로 쌓인 credential helper를 차례로 실행한다. 앞선 helper가 자격 증명을 주지 못하면 로컬 helper까지 실행된다 (확인). URL별 키(`credential.<url>.helper`)도 같다.
- **시나리오**: 악성 저장소의 `credential.helper = !<명령>`이 fetch 인증 과정에서 실행된다. 자격 증명을 가로채는 helper도 만들 수 있다.
- **대응** (ADR-0009):
  1. fetch에 `-c credential.helper=`(빈 값)을 넣어 그때까지 쌓인 목록을 비운다. URL별 helper도 함께 비워진다 (확인).
  2. 그 뒤에 신뢰 scope의 `credential.*helper` 항목을 **원래 순서와 키 그대로** 다시 넣는다. Apple 내장 `osxkeychain`과 `gh auth setup-git` 형식의 URL별 항목이 이렇게 복원된다 (확인).
  3. 순서가 중요하다. URL별 빈 값을 신뢰 helper보다 뒤에 넣으면 신뢰 helper까지 지워진다 (확인). 그래서 항상 "초기화 → 재삽입" 순서를 지킨다.
- **잔여 위험**: 신뢰 scope의 helper 자체가 위험하면 막지 못한다 (위협 모델 밖).
- **검증**:
  - SEC-T6-01 (로컬 generic helper → canary 없음)
  - SEC-T6-02 (로컬 URL별·와일드카드 helper → canary 없음)
  - SEC-T6-03 (신뢰 global helper와 URL별 helper가 순서대로 실행됨)
  - SEC-T6-04 (https promisor 원격의 lazy fetch: 앱 조회는 로컬 helper를 실행하지 않고 서버에 요청도 보내지 않음, 대조군은 401 뒤 helper 실행, #212)
  - SEC-T6-05 (실제 git: URL에 비밀번호가 든 원격(직접, 또는 `insteadOf` 바꿔치기로)은 앱 fetch가 git 실행 전에 거부하고 서버에 요청이 없음. 대조군은 그 URL로 접속. git 2.37+는 `-c transfer.credentialsInUrl=die`, 그 미만은 검사가 막음, #356)
  - SEC-T6-06 (git의 자격 증명 CVE 수정을 끄는 `credential[.<url>].protectProtocol`·`sanitizePrompt`는 fetch에서 `true`로 강제됨, #356)
- **상태**: 설계 완료
