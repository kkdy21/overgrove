# PB-3b·PB-4 그래프 스트리밍 (2026-11-08)

> 상태: 측정 기록 · 관련: #254, [ADR-0010](../../adr/0010-commit-graph-layout-in-app.md) 결정 3, [performance-budget.md](../performance-budget.md) PB-3·PB-3b·PB-4, [이전 측정](2026-11-07-pb3-graph-paging.md)

commit-graph 파일이 없는 저장소에서 그래프 페이지를 한 프로세스의 스트림으로 내주게 바꾼 뒤(#254), 앱이 실제로 쓰는 경로인 `RepositoryService.graphPage`로 다시 쟀다. PERF-03에 "app path" 행을 더했다.

## 환경

| 항목 | 값 |
|---|---|
| 장비 | Apple M1, 8코어, macOS 26.5.2 |
| git | Xcode 개발자 디렉터리의 `usr/bin/git` 2.50.1 (Apple Git-155), 앱과 같은 인자·환경, 격리한 HOME |
| 저장소 | `make-bench-repo.sh` 기본값(커밋 100,024개, 추적 파일 1만, 워크트리 10). commit-graph 없는 것과 `--commit-graph`로 만든 것 두 벌 |
| 측정 | PERF-03 (`GraphBenchmarkTests`). "app path"는 개요를 먼저 읽은 서비스에서 `graphPage`만 잰다. 첫 페이지는 서비스를 새로 만들어 11회(첫 회 버림), 스크롤은 서비스 하나로 끝까지 페이지 단위 |
| 부하 | 다른 에이전트 세션들의 빌드·테스트가 함께 돌았다(load average 10–17). 첫 페이지 p95는 그 영향이 크다 |

## 결과

**commit-graph 없음 (PB-3b)**

| 측정 | 값 |
|---|---|
| `--skip` 첫 페이지 (git 직접) | p50 410ms, p95 442ms |
| `--skip` 깊은 페이지 (500·1만·4만) | 중앙값 427–449ms (페이지마다 전체 정렬) |
| **앱 경로 첫 페이지** | **p50 474ms, p95 750ms** (PB-3b 1.0초 안) |
| **앱 경로, 스크롤 중 다음 페이지** | **p50 0.13ms, p95 0.22ms**, 최대 496ms(첫 페이지) |
| **앱 경로, 전체 이력을 페이지 단위로** | **1.8초** (201페이지; `--skip`이면 약 201 × 450ms ≈ 90초) |
| 페이지당 레이아웃 (메인 액터) | 최대 5.8ms / 프레임 16.7ms (PB-4) |

**commit-graph 있음 (PB-3) — 바뀌지 않음**

| 측정 | 값 |
|---|---|
| 앱 경로 첫 페이지 | p50 54ms, p95 58ms |
| 앱 경로, 스크롤 중 다음 페이지 | p50 54ms, p95 70ms, 최대 108ms (`--skip` 페이지) |

## 해석

- **PB-3b**: 첫 페이지는 스트림이 정렬을 마칠 때까지 기다리므로 `--skip`과 비슷하다(약 0.4–0.5초). 예산 1.0초 안이다.
- **PB-4**: 스트림이 들어오는 동안 다음 페이지는 이미 파싱된 커밋에서 나오므로, 스크롤 끝에서 기다리는 일이 사실상 없어졌다(0.2ms). 이전에는 페이지마다 약 450ms를 기다렸다. 프레임 비용은 레이아웃(최대 5.8ms)뿐이다.
- 스트림은 10만 커밋에서 멈추고(명령 상한), 나머지 24개는 `--skip`으로 읽혔다. 설계대로다. 전체 이력은 약 15MB이고, 스트림의 출력 상한은 64MB다.
- **정정**: 이전 기록의 "`--all`로 보이는 커밋 68,734개"는 한 프로세스 조회가 **10MB 조회 상한에서 잘린 값**이었다. bench 저장소의 실제 이력은 100,024개다. PERF-03은 이제 잘린 경우 그렇게 표시한다.
