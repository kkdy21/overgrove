# Apple Git 2.54 재측정과 추가 시나리오 (2026-11-06)

> 상태: 측정 기록 · 관련: #167, [benchmark-plan.md](../benchmark-plan.md), [performance-budget.md](../performance-budget.md), #54, #76, #91, #163, #168

기준 장비의 `/usr/bin/git`이 2.50.1에서 2.54.0으로 바뀌어, benchmark-plan.md §5 규칙("git 버전이 바뀌면 git 계층 기준값을 다시 잰다")에 따라 기준선을 다시 쟀다. 자동 새로고침(#163) 판단에 필요한데 기준선에 없던 상황도 함께 쟀다.

## 1. 환경

| 항목 | 값 |
|---|---|
| 장비 | Apple M1 Pro (10코어), 32GB, macOS 26.6.2 |
| git | `/usr/bin/git` 2.54.0 (Apple Git-157). 직접 실행은 `xcode-select -p` 아래의 `usr/bin/git`(Xcode 27.2). 직전 기준선의 직접 실행은 Command Line Tools 경로였다 |
| 저장소 | `make-bench-repo.sh --commit-graph` 기본값(커밋 100,024, 추적 파일 10,000, 워크트리 10), `make-bench-repo.sh --commits 3000 --files 100000 --worktrees 3`(추적 파일 10만 개) |
| 반복 | 기준선 20회, 시나리오 15회. nearest-rank p50/p95, 단위 ms, 프로세스 생성 비용 포함 |
| 주의 | 측정하는 동안 같은 장비에서 다른 작업(에이전트 세션)이 함께 돌았다. p95는 부풀었을 수 있으므로 비교는 p50 위주로 본다 |

## 3. 추가 시나리오 S1–S6 (직접 실행)

| ID | 시나리오 | p50 | p95 |

| S2 | status, 추적 파일 10만 개 | 150 | 170 |
| S3a | status, 파일 1만 개의 mtime만 바뀐 상태 (index 갱신 없음) | 276 | 328 |
| S3b | 같은 워크트리, 터미널 git이 index를 갱신한 뒤 | 29 | 38 |

모든 명령은 앱과 같은 공통 인자와 환경 변수로 실행했다(`--no-optional-locks`, `GIT_OPTIONAL_LOCKS=0` 포함).

## 4. 해석

1. **추적 파일 수에 거의 비례한다.** 1만 개에서 10만 개로 늘면 status가 28 → 150ms가 된다(약 5.4배). 10만 개짜리 워크트리 10개면 병렬 4로도 git만 0.5초를 넘길 수 있어, PB-1의 내부 목표(500ms)가 빠듯해진다.
2. **index가 오래된 상태(S3)가 가장 큰 위험이다.** 파일 내용은 그대로이고 mtime만 바뀌면, git은 그 파일을 다시 읽어 해시해야 변경 여부를 안다. 터미널의 `git status`는 그 결과를 index에 기록해 다음부터 빨라진다. 반면 앱은 에이전트와 `index.lock`이 부딪치지 않도록 index를 쓰지 않으므로 매번 다시 해시한다. 파일 1만 개면 p95 328ms로 PB-5(300ms)를 넘고, 10만 개면 5.2초다. 포매터, 코드 생성기, 빌드가 파일을 다시 쓰는 에이전트 작업에서 흔히 생긴다. 터미널이나 에이전트가 git 명령을 한 번 실행하면 원래 속도로 돌아온다(S3b, S3d). 앱은 index를 갱신하지 않고, 느린 status를 감지해 안내한다(#168).
3. **untracked 2만 개(S4)는 git 시간보다 출력 크기가 문제다.** git 시간은 47 대 27ms로 차이가 작지만 출력은 383KB 대 2.8KB다. 파싱과 모델 갱신 비용은 출력 크기를 따라가므로, 포커스가 없는 워크트리의 백그라운드 갱신에는 `normal`을 검토할 만하다(#91).
4. **로컬 브랜치 ahead/behind는 `for-each-ref` 한 번으로 충분하다(S5).** `%(upstream:track,nobracket)`을 붙여도 1ms 안팎만 늘어난다. 브랜치마다 `rev-list`를 실행하면 13개에 95ms(p95 127ms)가 들고, 그동안 동시 실행 슬롯을 차지한다. 브랜치가 많을수록 차이가 커진다(#54).
5. **설정 검사(S6)는 8ms다.** 캐시를 쓸 수 없는 저장소(`includeIf "onbranch:"`)에서 새로고침마다 실행해도 부담이 작다.

## 5. 자동 새로고침(#163)에 주는 의미

- FSEvents로 감시하면 변경이 없을 때 비용이 없다. 변경이 생기면 그 워크트리의 status 한 번이 든다(파일 1만 개 29ms, 10만 개 150–170ms).
- 같은 일을 주기 폴링으로 하면 변경이 없어도 워크트리 수만큼 status를 계속 실행한다. 5초 주기, 워크트리 10개 기준으로 1만 개 저장소는 한 코어의 약 6%, 10만 개 저장소는 약 32%를 쓴다. index가 오래된 10만 개 저장소에서는 status 한 번(5.2초)이 주기보다 길다.
- 따라서 자동 새로고침을 넣는다면 다음을 함께 갖춰야 한다: 창이 화면에 보일 때만 감시, 워크트리별 디바운스, 워크트리별로 한 번에 하나만 실행, 마지막 소요 시간에 비례한 재실행 간격(예: max(2초, 소요 시간 × 10)). 마지막 조건이 있으면 최악의 경우(5.2초)에도 52초에 한 번으로 묶여 한 코어의 약 10%를 넘지 않는다.

## 6. 재현

```sh
scripts/make-bench-repo.sh --commit-graph ~/tmp/overgrove-bench
scripts/make-bench-repo.sh --commits 3000 --files 100000 --worktrees 3 ~/tmp/overgrove-bench-100k
scripts/measure-git-baseline.sh -n 20 ~/tmp/overgrove-bench
scripts/measure-git-baseline.sh -n 20 --git "$(xcode-select -p)/usr/bin/git" ~/tmp/overgrove-bench
scripts/measure-git-scenarios.sh --git "$(xcode-select -p)/usr/bin/git" ~/tmp/overgrove-bench ~/tmp/overgrove-bench-100k
```

`measure-git-scenarios.sh`는 기준 저장소를 바꾼다(파일 mtime 변경, untracked 디렉터리 생성과 삭제, index 갱신). 다른 측정을 이어서 하려면 기준 저장소를 다시 만든다.
