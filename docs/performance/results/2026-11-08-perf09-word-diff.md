# S-10 단어 단위 강조의 비용 (PERF-09, 2026-11-08)

> 상태: 측정 기록 · 관련: #387, #122, [performance-budget.md](../performance-budget.md) PB-9, [screens.md](../../design/screens.md) S-10, [이전 측정](2026-11-07-s10-diff-viewer.md)

S-10이 단어 단위 강조와 공백 표시(#387)를 위해 행을 만들 때 표시(marks)도 함께 계산한다(`DiffDocument.unifiedRows(marked: true)`). 앱은 이 경로로 행을 만들므로 PERF-09도 이 경로를 잰다. 표시 계산이 PB-9(1만 줄 이하에서 파싱 + 행 p95 200ms 미만)를 넘지 않는지 확인했다.

- 입력: 이전 측정과 같은 합성 patch(20줄 hunk, 삭제·추가 반반, 줄마다 탭 1개 + 58자). 여기에 **줄마다 단어 하나가 다른** 1만 줄 patch를 더했다. 같은 내용의 줄 짝은 바이트 비교로 바로 건너뛰므로, 단어 비교를 실제로 거치는 경우를 따로 쟀다.
- 11회 실행에서 첫 회는 버렸다. `TEST_RUNNER_OVERGROVE_PERF=1`, `DiffViewerBenchmarkTests`.

## 환경

Apple M1 Pro, Debug 빌드 테스트 호스트(이전 측정과 같은 조건). 다른 에이전트 세션들이 같은 장비에서 빌드·테스트를 함께 돌렸다.

## 결과 (p95)

| 입력 | main(표시 없음) | 처음 구현 | 최적화 후 | PB-9 |
|---|---|---|---|---|
| 1만 줄: 파싱 + unified 행 | 70.0 ms | 274 ms | 98.5 ms | 200 ms |
| 1만 줄, 단어 다름: 파싱 + unified 행 | — | 251 ms | 155 ms | 200 ms |
| 500줄: 파싱 + unified 행 | 3.7 ms | 14.5 ms | 4.6 ms | 200 ms |
| 모든 크기: 첫 프레임 | 8.8–13.7 ms | — | 11.0–14.7 ms | 16 ms |

16만 줄(약 9.6MiB)은 큰 diff 확인(`Show Diff`) 뒤에만 행을 만든다. main 1,113ms, 최적화 후 1,085ms다.

## 무엇을 바꿨나

처음 구현은 1만 줄에서 PB-9를 넘었다. 다음을 고쳤다.

1. 한 줄의 표시 문자열을 표시 계산과 행 만들기에서 두 번 만들던 것을 한 번으로 줄였다.
2. 출력 가능한 ASCII와 탭만 있는 줄은 바이트 배열로 만든다. 이스케이프가 필요 없기 때문이다.
3. 단어 비교에서 두 줄이 공유하는 앞뒤 토큰은 표 없이 건너뛴다. 대부분의 수정은 단어 몇 개만 건드린다. ASCII 문자는 빠르게 분류하고, 토큰은 스칼라 버퍼에서 `memcmp`로 비교한다. 바이트가 같은 줄 짝은 비교하지 않는다.
4. 파일 하나에서 단어 비교를 하는 줄 짝의 상한을 5,000에서 **2,000**으로 낮췄다(`WordDiff.maximumPairedLinesPerFile`). 1~3만으로는 단어가 다른 1만 줄 patch가 234ms였다. 2,000짝(바뀐 줄 4,000개)을 넘는 diff에서는 그 뒤 줄을 줄 단위 배경으로만 보인다.

## 판단

- PB-9 안이다. 단어가 다른 1만 줄은 155ms다.
- 상한 변경(5,000 → 2,000)은 screens.md S-10의 설계 값과 다르다. #122 설계 문서가 머지된 뒤 S-10의 상한 문장을 이 값으로 고친다.
