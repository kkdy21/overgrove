# PB-1 워크트리 10개 병렬 조회 (2026-11-07)

> 상태: 측정 기록 · 관련: #87, [performance-budget.md](../performance-budget.md) PB-1·§4 권고 2, [overview.md](../../architecture/overview.md) §3.2·§4

`RepositoryService.loadOverview`가 PB-1의 git 계층을 한 번에 실행하는 데 걸린 시간을 쟀다. 실행 내용은 다음과 같다.
- `worktree list`
- 이어서 병렬로: 워크트리마다 (같은 저장소인지 확인하는 `rev-parse` → 그 워크트리의 `config --list` 검사 → `status`), `for-each-ref`, `stash list`

조회 동시 실행 한도(`GitClient`의 조회 풀)를 바꿔 가며 비교했다.

## 환경

| 항목 | 값 |
|---|---|
| 장비 | Apple M1, 8코어, macOS 26.5.2 |
| git | Xcode 개발자 디렉터리의 `usr/bin/git` 2.50.1 직접 실행. 앱과 같은 인자·환경(`GitEnvironment`), 격리한 HOME |
| 저장소 | `scripts/make-bench-repo.sh --commit-graph`. 커밋 약 8.6만, 추적 파일 1만, 워크트리 10개(메인 + `wt-00`–`wt-08`, 각각 WIP 변경 포함) |
| 측정 | `OvergroveTests/Performance/RepositoryOverviewBenchmarkTests`, `TEST_RUNNER_OVERGROVE_BENCH_REPO=<dir>`. 한도마다 21회 실행, 첫 회는 워밍업으로 버림. nearest-rank p95(20개 중 19번째). 프로세스 생성·파싱 포함, 렌더링 제외 |
| 주의 | 같은 장비에서 다른 에이전트 세션들이 빌드·테스트를 함께 돌렸다(load average 7–18). 그래서 여러 번 측정했다 |

## 최종 결과 (ms, `ProcessRunner` 수정 후 3회)

| 조회 한도 | p50 | p95 |
|---|---|---|
| 4 (이전 기본값) | 158–159 | 160–164 |
| **8 (새 기본값, min(코어, 8))** | 127–130 | 135–147 |
| 10 | 130–133 | 136–140 |
| 1 (참고, 수정 전) | 327–352 | 331–388 |

- **PB-1(1.0초 p95)을 크게 밑돈다.** 기본값으로 git 계층과 파싱은 p95 약 135–150ms다. 렌더링에 850ms 이상이 남고, 내부 목표 500ms 안이다.
- 직렬(한도 1)보다 약 2.5배 빠르다.
- 한도 8이 4보다 p50이 약 30ms(18%) 빠르다. 워크트리별 확인 단계(`rev-parse`, `config --list`)가 더해져 프로세스 수가 늘었기 때문에, 병렬도의 이득이 처음 측정(status만, 4와 8이 잡음 안)보다 커졌다.
- 워크트리별 확인 단계의 비용: 한도 4에서 p50 약 130 → 158ms, 한도 8에서 약 128 → 130ms다. 보안 검토(#221)에서 추가했고, 아래 결정 3에 이유가 있다.

## 수정 전에 보인 1초 지연 (`ProcessRunner`)

한도 8과 10에서 10번 측정 중 7번, 20개 샘플 가운데 1–2개가 **약 1,020–1,080ms**로 튀었다. 그래서 p95가 1.0초를 넘었다. 한도 4에서는 한 번도 없었다.
- **원인**: 지연이 `ProcessRunner`의 종료 확인 폴링 주기(1초)와 같았다. 폴링 주기를 200ms로 바꿔 보니 튄 값이 약 250ms로 줄었다. 그래서 다음 순서로 판단했다.
  - 동시 프로세스가 많을 때 종료 이벤트(dispatch process source)가 가끔 오지 않는다.
  - git은 파이프를 닫은 직후 종료하므로, 파이프 EOF 시점에 한 번 확인하는 것으로는 잡지 못한다(측정으로 확인).
  - 그러면 1초 폴링이 와서야 끝난다.
- **수정**: 두 파이프가 모두 닫혔는데 종료가 아직 안 보이면, 10ms마다 종료를 확인한다(`waitid` `WNOHANG|WNOWAIT`, 회수하지 않음). 자식이 곧 끝나는 순간에만 잠깐 돈다.
- **결과**: 수정 후 3회 측정에서 튀는 값이 없었다(load average 14–17).

## 결정

1. 조회 한도의 기본값을 **min(코어, 8), 최소 2**(`GitClient.defaultConcurrency`)로 바꾼다(#87 완료 조건). 이 장비에서는 8이다. 코어가 적은 장비에서는 코어 수를 넘겨 디스크를 다투지 않는다.
2. fetch는 지금처럼 별도 풀(앱 전체 2개)이다. 그래서 git 프로세스는 동시에 최대 min(코어, 8) + 2개다. 조회는 fetch를 기다리지 않는다(#76). 여러 저장소나 워크트리가 동시에 새로고침해도 한도는 `GitClient`에서 앱 전체에 한 번만 적용된다.
3. 워크트리 경로는 저장소가 쓰는 파일(`.git/worktrees/<id>/gitdir`)에서 오므로 믿지 않는다. 그래서 status 전에 두 가지를 확인한다.
   - 같은 저장소(공통 git 디렉터리)인지
   - 그 워크트리의 설정(`config.worktree` 포함)을 검사했는지

   이 비용은 측정에 포함했다.
