# ADR-0018: 실행 간 디스크 캐시는 표시 전용 워크트리 요약 스냅샷만 둔다

> 상태: Proposed · 날짜: 2026-11-08 · 관련: #328, #109, ADR-0008, ADR-0009, [overview.md §5·§8](../architecture/overview.md#5-캐시와-무효화), [security-review.md T19](../design/security-review.md#t19-디스크에-남는-저장소-데이터), [performance-budget.md PB-1](../performance/performance-budget.md)

## 맥락

v0.1의 결과 캐시(`RepositoryService`, overview.md §5)는 메모리에만 있다. 앱을 다시 실행하면 마지막 저장소를 자동으로 열지만(`restoreLastSelected`), 캐시가 비어 있어서 첫 조회가 끝날 때까지 사이드바와 그래프가 비어 있다. 첫 조회는 git 15~25회와 파싱을 거치고, 워크트리 10개 기준 git 계층만 p95 약 135~150ms다(PB-1 측정). 큰 저장소나 느린 디스크에서는 더 길다.

#109는 이 빈 화면을 줄이려고 디스크 캐시를 검토한다. 완료 조건은 "비밀 정보 미저장, 무효화 규칙"이다. 디스크 캐시는 지금까지 없던 성질을 들여온다.

- 저장소 데이터가 앱이 닫힌 뒤에도 디스크에 남는다. 지금 디스크에 남는 것은 `UserDefaults`의 저장소 경로, 패널 배치, fetch 기록뿐이다(overview.md §8).
- 앱이 다음 실행 때 읽는 파일이 하나 늘어난다. 그 파일은 같은 계정의 다른 프로세스가 바꿀 수 있다.
- 오래된 값을 보여 줄 수 있다. 보안 판단(설정 검사, ADR-0009)에 쓰이면 위험하다.

그래서 무엇을 저장하고 무엇을 저장하지 않을지, 언제 버릴지, 읽을 때 어떻게 다룰지를 구현 전에 정한다. 새 위협은 [security-review.md T19](../design/security-review.md#t19-디스크에-남는-저장소-데이터)로 추가한다.

## 결정

**저장소마다 사이드바 WORKTREES를 그릴 만큼의 요약(`LaunchSnapshot`)만 `~/Library/Caches/<bundle id>/LaunchSnapshots/`에 JSON으로 저장한다. 다음 실행에서 그 저장소를 열 때 이 요약을 "갱신 중" 상태로 먼저 그리고, 평소의 `.user` 조회를 그대로 실행한다. 스냅샷은 표시에만 쓰고, 어떤 명령이나 보안 판단에도 쓰지 않는다.**

### 1. 저장하는 것 (allowlist)

`LaunchSnapshot`은 전용 `Codable` 타입이다. `RepositoryOverview`, `WorkingState`, `RepoConfigInspection`을 그대로 인코딩하지 않는다. 필드를 하나씩 골라 담아서 새 필드가 실수로 디스크에 가지 않게 한다.

| 필드 | 내용 | 비고 |
|---|---|---|
| 머리 | 형식 버전, 앱 버전·빌드, git 버전, 저장 시각, 저장소 ID의 SHA-256 | 무효화(§3)에 쓴다 |
| 워크트리 행 (최대 64개) | 경로, main 여부, 브랜치 짧은 이름 또는 detached, HEAD 짧은 SHA, 잠김·prunable 여부 | 64는 한 번에 조회하는 워크트리 상한(`defaultMaximumQueriedWorktrees`, T15)과 같다 |
| 행의 개수 | 변경 파일 수, untracked 수, 충돌 수, ahead·behind, upstream 없음·사라짐 여부 | 숫자와 상태만. upstream 이름은 저장하지 않는다 |
| 저장소 | stash 개수, 포커스 워크트리 경로 | |
| 지문 | §3의 파일들의 `stat` 값 | |

### 2. 저장하지 않는 것

- config 값, 설정 검사 결과(`RepoConfigInspection`), 원격 이름과 URL, 자격 증명, 경고·오류 문구, stderr
- 파일 경로·이름(작업 트리 안), 커밋 제목·작성자·이메일, stash 메시지, 그래프 페이지, 커밋 상세, 이슈, diff
- upstream 브랜치 이름과 다른 ref 이름. 브랜치 짧은 이름은 행 제목이라 저장한다

그래프 첫 페이지(PB-3)도 체감에 크지만 커밋 제목·작성자 이메일을 디스크에 남기게 된다. 이번 결정에서는 제외하고, 측정(§7) 뒤에 따로 결정한다.

### 3. 무효화

다음 중 하나라도 맞으면 스냅샷을 보여 주지 않고 지운다.

- 형식 버전, 앱 버전·빌드, git 버전이 지금과 다르다.
- 파일 머리의 저장소 ID 해시가 파일 이름(지금 저장소 ID의 해시)과 다르다.
- 지문이 다르다. 지문은 공통 git 디렉터리의 `HEAD`, `packed-refs`, `config`, `worktrees/` 디렉터리와, 각 워크트리 git 디렉터리의 `HEAD`, `index`에 대한 `lstat(2)`의 장치·inode·크기·mtime·ctime이다(설정 검사 캐시와 같은 방식, overview.md §5). 없던 파일이 생기거나 있던 파일이 사라져도 다르다.
- 저장한 지 7일이 지났다.
- 파일이 §4의 검증을 통과하지 못한다.

지문이 같아도 작업 트리만 바뀐 경우(index를 건드리지 않는 수정)는 잡지 못한다. 그래서 스냅샷은 항상 "갱신 중"으로 그리고, 숫자는 첫 조회가 끝나면 바뀐다.

다음 때는 파일을 지운다: 저장소 제거(`forget`), 그 저장소의 새로고침 실패(지금도 메모리 캐시를 버리는 조건), 설정 검사가 조회를 막을 때.

쓰는 때: 그 저장소의 `.user`·`.automatic`·`.fetchCompleted` 조회가 성공한 뒤, 최대 10초에 한 번(디바운스). 원자적으로 쓴다(임시 파일 후 rename).

### 4. 읽을 때: 신뢰하지 않는 입력

같은 계정의 다른 프로세스가 파일을 바꿀 수 있다. 계정 장악은 위협 모델 밖이지만(security-review.md §1.2), 파일은 git 출력처럼 신뢰하지 않는 입력으로 다룬다.

- 일반 파일이고(심볼릭 링크 거부, `lstat`), 크기가 256 KiB 이하일 때만 읽는다.
- `JSONDecoder`로 고정 스키마를 읽는다. 알 수 없는 형식 버전, 빠진 필드, 범위를 벗어난 숫자(음수, 1,000,000 초과), 64개를 넘는 행이면 전체를 버린다.
- 경로는 제어 문자가 없는 절대 경로만, 문자열은 길이 상한(경로 1,024자, 브랜치 이름 256자) 안에서만 받고, 화면에는 `PathValidator.displayable`을 거친다.
- 등록된 저장소에 속한 경로만 쓴다. 스냅샷의 워크트리 경로로 아무것도 실행하지 않는다(§5).
- 실패하면 조용히 버리고 파일을 지운다. 로그에는 이유 분류만 남긴다(T16).

### 5. 표시 전용

- 스냅샷으로 그린 행은 "갱신 중"(첫 조회 중과 같은 표시)이고, 첫 조회 결과가 오면 통째로 바뀐다.
- 스냅샷 상태에서는 git이나 외부 앱을 부르는 동작을 막는다: 행 메뉴의 Reveal in Finder·Open in Terminal·Compare, 툴바 Terminal·Finder·Compare, S-02·S-05 상세. 상세 패널은 첫 조회 결과를 기다린다.
- 스냅샷은 `RepoSafetyContext`, 설정 검사 캐시, `TerminalGuard`, fetch 판단에 들어가지 않는다. 첫 조회는 스냅샷과 관계없이 평소처럼 설정 검사부터 시작한다.

### 6. 위치와 권한

- `FileManager`의 Caches 디렉터리(`~/Library/Caches/<bundle id>/LaunchSnapshots/`). 시스템이 공간이 부족하면 지울 수 있는 곳이고, 없어져도 첫 화면이 조금 늦을 뿐이다. 앱은 샌드박스를 쓰지 않으므로(`Config/Overgrove.xcconfig`) 컨테이너 경로가 아니다.
- 디렉터리는 `0700`, 파일은 `0600`으로 만든다.
- 파일 이름은 저장소 ID(공통 git 디렉터리 경로)의 SHA-256 16진수다(`PanelLayoutStore`와 같은 방식). 디렉터리 목록에 저장소 경로가 보이지 않는다. 파일 안에는 워크트리 경로가 있다. 경로는 이미 `UserDefaults`(저장소 목록)에도 있는 정보다.

### 7. 성능 측정과 진행 조건

구현 PR(#109)은 먼저 측정한다.

- 새 측정 항목: 앱 실행 → 마지막 저장소의 워크트리 목록 첫 프레임. 스냅샷 있음·없음, 워크트리 10개(`scripts/make-bench-repo.sh`), 10회 p50·p95.
- 스냅샷 쓰기와 읽기 비용: 64행 기준 쓰기·읽기·검증 각각 p95.
- **진행 조건**: 스냅샷이 첫 프레임 p95를 150ms 이상 줄이지 못하면 구현을 멈추고, 이 ADR을 Rejected로 바꾸는 PR을 낸다. 측정 결과는 `docs/performance/results/`에 남긴다.

## 대안

| 대안 | 장점 | 단점 | 기각 이유 |
|---|---|---|---|
| 디스크 캐시를 두지 않는다 | 디스크에 남는 데이터 없음, 새 위협 없음 | 재실행마다 첫 조회 동안 빈 화면 | 측정 전에는 판단할 수 없다. §7의 진행 조건으로 이 대안을 열어 둔다 |
| `RepositoryOverview` 전체를 그대로 인코딩 | 구현이 쉽고 상세 패널까지 바로 그림 | 파일 이름, 설정 검사 결과, upstream 이름, 오류 문구까지 디스크에 남음. 새 필드가 생기면 함께 저장됨 | 비밀 정보 미저장을 타입으로 보장할 수 없다 |
| 그래프 첫 페이지까지 저장 | PB-3(500ms)까지 줄어 체감이 큼 | 커밋 제목·작성자 이메일이 디스크에 남음. 크기가 커짐(500행) | 저장소 내용이 디스크에 남는 범위가 커진다. 측정 뒤 별도 결정 |
| 스냅샷으로 보안 판단까지 건너뜀(설정 검사 생략) | 첫 조회가 더 빨라짐 | 오래되거나 바꿔 넣은 결과로 git을 실행할 수 있음 | ADR-0009의 fail closed 원칙과 충돌 |
| `~/Library/Application Support`에 저장 | 시스템이 지우지 않음 | 다시 만들 수 있는 데이터를 백업·보존 대상에 둠 | 잃어도 되는 캐시는 Caches가 맞다 |
| SQLite·Core Data | 질의, 부분 갱신 | 저장소당 수 KB 요약에는 과함. 손상 처리 범위가 커짐 | JSON 파일 하나로 충분하다(ADR-0006: 외부 의존성 없음은 둘 다 만족) |

## 결과

- 좋아지는 점
  - 재실행 직후 마지막 저장소의 워크트리 목록이 바로 보인다(측정으로 확인).
  - 저장하는 필드를 타입이 정하므로 "비밀 정보 미저장"을 테스트로 고정할 수 있다.
  - 스냅샷이 표시 전용이라 오래되거나 바뀐 파일이 보안 판단에 끼어들 수 없다.
- 나빠지는 점, 감수하는 비용
  - 워크트리 경로, 브랜치 이름, 변경 수가 앱이 닫힌 뒤에도 사용자 계정의 Caches에 남는다(권한 `0600`). 저장소를 제거하면 지운다.
  - 스냅샷 상태의 짧은 동안 행 동작이 막힌다.
  - 지문으로 잡지 못하는 작업 트리 변경은 첫 조회 전까지 옛 숫자로 보인다("갱신 중" 표시).
  - 쓰기·읽기·검증 코드와 테스트를 유지해야 한다.
- 다시 검토해야 하는 조건
  - §7의 측정에서 이득이 기준에 못 미칠 때(Rejected로 바꿈)
  - 그래프 첫 페이지나 상세 패널까지 저장하자는 요구가 생길 때(새 ADR)
  - 앱이 샌드박스를 쓰게 될 때(위치가 컨테이너로 바뀜)
