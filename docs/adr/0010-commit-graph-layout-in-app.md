# ADR-0010: 커밋 그래프 레인은 앱에서 계산한다

> 상태: Accepted (Phase 2 게이트, 2026-11-05; 결정 3 갱신 2026-11-08, #254; 결정 5 개정 2026-11-08, #384) · 날짜: 2026-11-05 · 관련: G6, G9, PB-3, PB-3b, PB-4, [architecture/parsing-spec.md](../architecture/parsing-spec.md)

## 맥락

HANDOFF §9는 그래프에 `log --all --graph --date-order -z`를 적었다. `--graph`의 ASCII 출력에는 다음 문제가 있다.

1. 그래프 문자와 커밋 데이터가 한 줄에 섞여 파싱이 깨지기 쉽다. `-z`와 함께 쓰면 줄 구조도 흐트러진다.
2. 레인 색과 위치를 앱이 통제하지 못한다. 자체 렌더링(디자인 토큰의 레인 색)을 할 수 없다.
3. 10만 커밋에서 git이 전체 그래프를 그린 뒤에야 첫 화면을 그릴 수 있다. 페이지 단위로 불러올 수 없다 (PB-3).

또 `--all`은 `refs/stash`도 포함한다. 그래서 stash 커밋과 그 index·untracked 부모가 그래프에 섞인다 (실험으로 확인).

## 결정

1. 그래프 데이터는 `git log --exclude=refs/stash --all --date-order -z --format=%H%x00%P%x00%an%x00%ae%x00%at%x00%s`로 받는다. `--graph`는 쓰지 않는다. (#308에서 ref 범위를 `--branches --remotes --tags --exclude=refs/* --all`로 좁혔다: 브랜치·원격·태그·워크트리 HEAD만 따라가고 notes·prefetch·`refs/original`은 그래프에 넣지 않는다. 최신 인자는 [git-command-catalog.md](../architecture/git-command-catalog.md)가 기준이다.)
2. `GraphEngine`(UI 무관 순수 Swift)이 커밋 순서와 부모 목록(`%P`)으로 레인을 계산한다. 결과는 행별로 다음을 담는다.
   - 노드 열
   - 지나가는 선
   - 병합·분기 연결선
   - 레인 색 인덱스
3. **페이지 단위로 불러온다.**
   - 첫 페이지 500개(`-n 500`)를 먼저 그린다.
   - 다음 페이지는 같은 명령에 `--skip=<n> -n 500`을 붙여 읽는다. ref 집합이 같으면 순서가 결정적이므로, 엔진이 열린 레인 상태를 유지한 채 이어서 계산한다. ref 집합 해시가 바뀌면 처음부터 다시 계산한다.
   - **commit-graph 파일이 없으면 한 프로세스를 스트리밍한다(#254, 2026-11-08).** `--date-order`는 commit-graph 없이는 첫 줄을 내기 전에 전체 이력을 정렬하므로, `--skip` 페이지마다 그 비용(bench 약 430ms)을 다시 냈다.
     - `graphStream`(`--skip` 없는 같은 명령, `-n 100000`) 하나를 ref 집합마다 띄운다. ref 범위와 포맷은 `graphPage`와 한 헬퍼(`ReadOnlyGitCommand.graphRevisionArguments`)에서 만든다. 그래서 스트림 페이지와 `--skip` 대체 페이지가 같은 커밋을 같은 순서로 낸다(#308 범위 포함). stdout을 받는 대로 레코드 단위로 파싱하고(`GraphStreamParser`, 7개 NUL = 1 레코드), 페이지는 그 결과에서 내준다. 정렬은 한 번만 한다.
     - 상한은 stdout 64MB·타임아웃 120초·취소다(`ProcessLimits.stream`). 스트림이 커밋 상한(10만)·출력 상한·타임아웃·실패로 일찍 멈추면, 그 뒤 페이지는 `--skip`으로 읽는다.
     - commit-graph 유무는 공통 git 디렉터리의 `objects/info/commit-graph` 또는 `commit-graphs/commit-graph-chain` 파일로 판정한다. 파일이 있으면 지금처럼 `--skip` 페이지(약 50ms)를 쓴다.
     - ref 집합이 걸러진 ref나 잘린 목록 때문에 완전하지 않으면(`GraphRefSet.isComplete`가 false, #333) 스트림을 쓰지 않고 모든 페이지를 `--skip`으로 읽는다. 스트림은 ref 집합마다 하나를 두므로 캐시와 같고, 그 ref 집합으로는 걸러진 ref가 움직인 것을 알 수 없기 때문이다.
     - **페이지가 ref 집합과 같은 히스토리 상태에서 나왔는지 확인한다(#373).** ref 집합은 캐시된 overview에서 만들지만 `log`는 실행 시점의 ref를 읽는다. 그래서 새로 읽은 `--skip` 페이지마다, 그리고 스트림마다 한 번(첫 페이지가 온 뒤) ref와 워크트리 목록을 다시 읽어 ref 집합과 비교한다. 다르면 그래프는 방금 읽은 새 ref를 기억하고(`graphLiveRefs`, overview가 바뀌거나 ⌘R·저장소 정리 때까지) 그 ref 집합으로 페이지를 한 번 더 읽는다. overview는 건드리지 않는다. 그래프가 새로고침을 띄우면 대기 중인 창 활성화 새로고침을 밀어낼 수 있기 때문이다. ref 집합이 바뀌었으므로 `GraphStore`는 이어 붙이지 않고 처음부터 다시 읽는다. 그 사이에 또 움직였으면 그 페이지는 불완전한 ref 집합처럼 다룬다(캐시하지 않고, 다음 새로고침에서 처음부터 다시 읽음). 비용은 캐시되지 않은 페이지마다 `for-each-ref`와 `worktree list` 한 번씩이다. 두 읽기 사이에 움직였다가 제자리로 돌아온 ref는 알아채지 못한다.
     - 화면(`GraphStore`)과 `GraphLoading` 인터페이스는 그대로다. ⌘R과 저장소 정리는 스트림을 멈추고 버린다.
     - 스트림은 앱 전체에서 한 번에 하나만 돈다(조회 슬롯과 따로, `GitClient`의 stream 슬롯). 그래서 오래 걸리는 스트림이 status·diff 조회를 막지 않는다. 다른 저장소의 스트림을 시작할 때는 아직 끝나지 않은 스트림을 멈춘다. 그 스트림의 대기 중인 페이지는 `--skip`으로 읽고, 그 저장소를 다시 열면 스트림을 새로 시작한다. 그래서 새 저장소의 첫 페이지가 다른 저장소의 스트림 뒤에서(최대 120초) 기다리지 않는다. 끝난 스트림의 커밋은 저장소 2개까지만 들고 있는다(PB-6).
4. 레인 색은 **레인이 처음 생길 때의 열 인덱스 mod 8**로 정하고, 그 레인이 끝날 때까지 바꾸지 않는다. 색은 디자인 토큰 `graph.lane.0`~`graph.lane.7`이다 ([design/design-tokens.md](../design/design-tokens.md)). 페이지를 이어 읽어도 기존 레인의 색은 유지된다.
5. v0.1은 stash 노드를 그래프에 그리지 않는다. stash는 사이드바와 S-04에서만 보여 준다.
   - **개정 (#384, v0.2.0).** stash를 WIP 행(§6)처럼 GraphEngine 밖 가상 행으로 그린다. 그래프 데이터 명령은 계속 `refs/stash`를 빼고, 엔진 입력·레인·페이지 계산은 바뀌지 않는다.
   - stash 행은 기준 커밋(첫 부모) 바로 위에 끼워 넣는다. 기준 커밋 레인 색의 속 빈 사각 노드와 기준 커밋으로 가는 점선을 그리고, index·untracked 부모는 그리지 않는다. 그 사이를 지나가는 레인은 stash 행을 곧게 통과한다(곡선은 두 레인의 중간에서 통과).
   - 같은 기준 커밋의 stash는 `stash@{n}` 순서로 위에서부터 쌓는다. 기준 커밋이 로드된 페이지에 있을 때만 보이고, 그래프 범위 밖(브랜치·태그·워크트리 HEAD에서 닿지 않음)이면 사이드바에만 있다.
   - 그래프 `⋯` 메뉴의 `Show Stashes`로 켜고 끈다(기본 켬, 앱 전역). 검색·작성자 필터 중에는 숨긴다. 누르면 사이드바에서 고른 것처럼 S-04를 연다.
6. WIP 행은 GraphEngine 밖에서, 선택한 워크트리의 HEAD 위에 가상 행으로 얹는다.
7. 서명 관련 포맷(`%G?`, `%GS` 등)은 쓰지 않는다 (T7).

## 대안

| 대안 | 장점 | 단점 | 기각 이유 |
|---|---|---|---|
| `--graph` ASCII 파싱 | 구현이 빠름 | 파싱 취약, 페이지 불가, 색 통제 불가 | 위 맥락 |
| `--topo-order` | 브랜치별로 묶여 보임 | 큰 저장소에서 첫 출력이 느림 (전체 정렬 필요) | PB-3. `--date-order`도 전체 정렬이 필요할 수 있어 Phase 3에서 측정 |
| commit-graph 파일 직접 읽기 | 매우 빠름 | 자체 Git 엔진에 가까움 | N5 |

## 결과

- 그래프 모양을 테스트(GRA-xx)로 고정할 수 있고, 렌더링을 자유롭게 바꿀 수 있다.
- 레인 계산 알고리즘을 직접 구현·유지해야 한다. 문어발 병합(octopus), 고아 브랜치, 매우 긴 레인 등 경계 사례를 테스트로 다룬다.
- `--date-order`의 첫 출력 지연은 저장소 크기에 따라 다르다. `scripts/make-bench-repo.sh`로 측정한 결과에 따라 정렬 옵션을 조정한다.
