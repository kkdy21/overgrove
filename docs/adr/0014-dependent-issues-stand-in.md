# ADR-0014: 의존 이슈를 기다리지 않는다 — stand-in으로 먼저 개발하고 머지만 순서대로

> 상태: Accepted · 날짜: 2026-11-06 · 관련: #ISSUE_NO, [ADR-0013](0013-external-contributions-and-issue-claiming.md), [process/collaboration.md §4.1](../process/collaboration.md#41-의존-이슈가-아직-끝나지-않았을-때)

## 맥락

이슈 A를 하려면 이슈 B의 결과물이 필요한 경우가 많다. 예를 들어 #65(워크트리 목록)에는 #64(메인 창)와 #50·#51(파서)이 필요하다. 지금까지는 B가 머지되어 닫혀야 A를 시작할 수 있었고, `/onboard`는 열린 의존성이 있는 이슈를 추천에서 뺐다.

여러 협업자가 AI 에이전트로 동시에 개발하면 이 방식이 맞지 않는다.

- B가 언제 머지될지 모른다. 머지는 메인테이너 혼자 하고, B가 반려되거나 닫힐 수도 있다.
- 의존 사슬이 길다. #35 → #64 → #68 → #69 → #70은 머지를 다섯 번 기다려야 끝까지 간다.
- 작업하다가 의존성을 발견하기도 한다. 그런데 협업자는 저장소 권한이 없어서 `status:blocked` 라벨을 붙이거나 이슈 본문을 고칠 수 없다.

B의 PR 브랜치를 내 브랜치에 merge해서 그 위에 쌓는 방법(stacked PR)은 쓰지 않는다. 남의 PR을 받아 오면 그 PR이 넣은 `.githooks/*`, `.claude/` hooks, 테스트 코드가 내 PC에서 실행된다. 메인테이너에게 외부 PR 체크아웃을 금지한 것([pull-requests.md §7](../process/pull-requests.md#7-외부-pr을-안전하게-검토하기))과 같은 위험이다.

## 결정

**의존 이슈가 끝나지 않았어도 기다리지 않는다. 필요한 부분은 자기 브랜치에 stand-in(임시 구현)으로 직접 만들어 개발하고, PR은 자기 이슈만 닫는다. 머지만 의존 순서대로 한다.**

1. 열린 의존성이 있어도 선점할 수 있다. `/onboard`는 의존성이 끝난 이슈를 먼저 추천하고, 의존성이 남은 이슈도 후보에 넣는다.
2. 남의 미머지 코드는 가져오지 않는다. B의 PR을 merge하거나 체크아웃하지 않는다. B에 PR이 있으면 diff를 읽어 이름과 시그니처를 맞추는 데만 쓴다.
3. stand-in은 A에 필요한 최소한만 만들고, 블록마다 `STAND-IN(#<B>)` 주석을 단다. B가 머지되면 지우고 실제 코드에 맞춘다.
4. 아무도 선점하지 않은 B는 직접 선점해서 B부터 PR을 올려도 된다. 이때 A 브랜치에는 내 B 브랜치를 merge한다. 내 코드라서 2의 위험이 없다.
5. A의 PR은 B가 끝날 때까지 Draft로 둔다. 순서가 뒤바뀌어 머지되지 않도록 `pr-policy`가 다음 경우에 실패한다.
   - 의존 이슈가 열려 있다. 의존 이슈는 연결 이슈 본문의 `## 의존성` 절과 PR 본문의 `Depends on #<n>` 줄에 있는 이슈다.
   - 의존 이슈가 완료가 아닌 사유(중복, not planned)로 닫혔다. 메인테이너가 아닌 사람이 완료로 닫은 경우도 끝난 것으로 보지 않는다. 머지는 메인테이너만 하기 때문이다.
   - 의존 이슈가 20개를 넘는다.
   - 추가된 줄에 `STAND-IN(#<n>)`이 남아 있다.
6. 메인테이너가 의존 이슈를 닫으면 `dependency-closed` 워크플로우가 그 이슈에 의존하는 열린 PR마다 댓글을 단다. 다른 사람이 이슈를 닫거나 다시 열어도 봇은 아무것도 하지 않는다. 작성자는 main을 합치고, stand-in을 지우고, 테스트를 돌린 뒤 Ready로 바꾼다.
7. 작업 중에 발견한 의존성은 PR 본문에 `Depends on #<n>`으로 적는다. 아직 이슈가 없으면 A 이슈에 댓글로 메인테이너에게 이슈를 요청하고, stand-in으로 계속 진행한다.

## 대안

| 대안 | 장점 | 단점 | 기각 이유 |
|---|---|---|---|
| 의존 이슈가 닫힐 때까지 시작하지 않는다(기존) | 단순하다 | 머지를 기다리는 동안 사람과 에이전트가 멈춘다. 사슬이 길면 대기가 쌓인다 | 병렬 개발의 이점이 사라진다 |
| 남의 미머지 PR 위에 쌓는다(stacked PR) | 실제 B 코드 위에서 개발한다 | 검수 전인 남의 코드가 내 PC에서 실행된다. B가 바뀔 때마다 다시 합쳐야 한다 | 보안 위험. 자기 B는 예외다(결정 4) |
| A의 PR에 B를 함께 구현한다 | 기다릴 필요가 없다 | B를 두 번 구현하고 두 번 리뷰한다. 선점 규칙과 충돌한다 | 중복 비용 |
| GitHub 네이티브 issue dependency(blocked by)로 관리한다 | GitHub 화면에 관계가 보인다 | 기존 이슈 90개의 `## 의존성` 절을 옮겨야 한다. 협업자는 관계를 편집할 수 없다 | 지금은 본문 절로 충분하다 |

## 결과

- 좋아지는 점
  - 의존 이슈의 진행 상황과 상관없이 바로 개발을 시작한다.
  - 실수로 순서가 뒤바뀌어 머지되는 것을 `pr-policy`가 막는다.
  - B가 언제 머지될지 몰라도 봇이 알려 준다.
- 감수하는 비용
  - stand-in을 만들고, B가 머지된 뒤 실제 코드에 맞추는 작업이 든다. B가 리뷰에서 많이 바뀌면 그만큼 고칠 것도 늘어난다.
  - 기다리는 Draft PR은 `pr-policy` 실패로 표시된다. 의도한 표시다.
  - `pr-policy`는 협조하는 기여자의 실수를 막는 장치이지 보안 경계가 아니다. fork PR은 자기 워크플로우 파일로 검사를 돌리고, GitHub는 바이너리나 아주 큰 파일의 patch를 주지 않으며, 표시를 조금만 바꿔도 stand-in 검사를 피할 수 있다. 검사는 PR 이벤트에서만 다시 돌기 때문에 통과한 뒤 의존 이슈가 다시 열려도 초록으로 남는다. 최종 확인은 메인테이너 검수(`/pr-review`)가 맡는다.
  - 기다리는 PR이 72시간 동안 갱신되지 않으면 담당자 지정이 풀린다(ADR-0013). 그래도 열린 PR이 있는 동안에는 다른 사람이 그 이슈를 선점하거나 PR을 낼 수 없고, 다시 push하면 `claim-expiry`가 담당자를 되돌린다.
- 다시 검토할 조건
  - 기다리는 PR이 쌓이면 메인테이너는 다른 PR이 기다리는 PR부터 머지한다(`/pr-review`). 그래도 쌓이면 동시 선점 한도(2개)를 다시 본다.
